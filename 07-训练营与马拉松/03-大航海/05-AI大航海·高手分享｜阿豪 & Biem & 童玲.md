**调研1：100个AI案例**

**调研2：AI应用场景**

**调研3：专家调研**

**调研4：用户调研**

> 1. 效率革命：自动化替代重复劳动：**A提速**
> 2. 数据驱动：精准决策替代经验判断
> 3. 能力突破：打破人力 / 时间 / 专业壁垒：**S探索**
> 4. 成本重构：降低投入、提升回报比：**R落地**
> 5. 模式革新：重构业务流程与盈利逻辑：**T变革**
> 核心本质：用技术放大能力边界，以更少资源创造更大价值。

### 三轮PRD迭代

调研之后，我们有了一些初步的结论，写了第一版粗糙的PRD。

>

#### PRD 1.0

**目标：**

1. 对一堂有价值
2. 对一堂同学有价值
3. 用户的感知（一眼看到哇擦牛逼，或者至少质量好坏可以鉴别）
4. 技术有门槛（有其他团队竞争的情况下有优势）

**受众：**

**价值：**

1. 所以我觉得对一堂来说体现到实际价值上的就是增加**课程销售量和降低脱课率**，可能这个Agent放到公域上去，也是一种引流手段（通过问题来对课程产生兴趣），当然也都是基于能够真正让用户感受到价值**R落地**
2. 用户的需求是解决自己的各种问题，一堂恰好有解决问题的答案，Agent作为中间的桥梁，自动化把成本打下去，智能化提高用户体验**A提效S探索**

**风险：**

**壁垒：**

1. 技术壁垒

   1. 低代码智能体平台+全量课程实现：人力投入巨大，工作量难以复制 #自研自动化工具可降低人力
   2. 重量级开发：生产级代码部署落地，技术架构复杂，环境无法复刻 #未知的研发周期是致命缺陷
2. 数据壁垒

   1. 结构化的知识库、私有的数据库，提供精细化信息源，提高 Agent 输出质量，输出有特色有价值的内容
   2. 一堂方法论模型结合具体场景的案例和跨学科模型，产生适配用户问题的组合模型

**技术路径**

## 回看

首先，我给这个项目定义的**开发难度是中低**，任何同学都可以简单复刻改造。

按照传统的软件架构去看，这是一个典型的前后端应用，而且未来会带个后台管理。

前端就是 Coze 的低代码界面，后端就是几个工作流，后台管理就是利用飞书多维表格的表单功能。

工作流中目前是包含了数据库的，未来要将数据部分分离出去，实现完全用飞书多维表格来进行数据管理。

用户界面和工作流只是在数据层上的外壳，用交互层和逻辑层组成的外壳，包裹住由一堂全部课程数据形成的内核，把动和静分开，或者反过来说，把静和动分开，是这个应用在我想象中的最佳状态。

- *在业务未形成时，逻辑是动态的，而数据是静态的。*
- *当业务已成型时，逻辑是静态的，而数据是动态的。*

后续，一堂只需要用一个表单，将新上架的课程内容填写后，用户就可以获得更新后的课程推荐了。

例如，某一天，一堂上架了一门**「重新理解：科学选址」**，原来智能体推荐不到的课程，就会因为更新了数据，能够为需要开线下店的同学推荐课程了。

可能之前为他推荐的课程是一些围绕着答案，但没有直击答案的课程，他需要根据已有条件去自己摸索出来答案，例如去学「深度思考」「调研黑客」甚至「科学送礼」，学明白后自己再交叉验证得到一个模糊的答案。甚至因为更着急，智能体也没及时更新课程，导致用户去友商那里找课了。

如果现在有了最对口的答案、针对性的课程后，直接推荐给他了，他就可以节省很多时间，直接学到「一堂选址五步法」模型，然后套公式就好了。

### 锁定技术路线

#### 开发方式

刚开始的时候，我们小队开会讨论，并且在和于陆老师沟通后，确认了用 Coze 作为最终的开发平台。

主要原因有三：

1. **成本：**Coze 门槛低，不涉及环境搭建、软件部署、后续运维的问题。
2. **影响：**一堂 AI 俱乐部几乎就是在 Coze 上走出来的，所有的一堂同学都熟悉 Coze 平台
3. **效率：**如果动代码开发，需要频繁和一堂研发协作，沟通成本高，职责从我们小队溢出，最终可能导致效率低下（而且有种客户钻进后厨逛游的感觉），而 Coze 本身是字节系的产品，天然和飞书产品线无缝融合，一堂又是深度飞书用户，后面用多维表格当 API 其实效果足矣。

#### 产品形态

同学们都知道 Coze 的项目开发存在两个选项：

- **Coze 智能体：**对话式，用户像在微信聊天一样，输入任何内容，AI灵活回复。
- **Coze 应用：**交互式，像填表单一样，用户输入特定信息，系统给出一个确定的结果。

【思考🙋‍♂️】怎么选呢？

作为一个技术开发者，我本能地想选智能体，因为明显智能体不用管前端的事：）

但是，站在产品体验的角度上，我们很清楚需要选什么。

# 课程推荐助手（结合课程表字段的上下文工程化工作流）

关键字段来源于课程表（清洗）：
- 课程方向 / 所处阶段 / 核心训练 / 课程名称 / 主讲人
- 推荐谁学 / 交付模型 / 完成作业后解锁candy / 选课链接

映射思路（抽取 → 对齐 → 排序 → 解释）：
- 抽取：角色、阶段、目标、痛点、关键词、期望交付、时间预算（可选）
- 对齐：与课程的 课程方向 / 所处阶段 / 核心训练 / 推荐谁学 / 交付模型 匹配
- 排序：多维启发式打分 + 去重 + 覆盖率（题→课）提升
- 解释：展示“匹配原因”，保证可解释性
'''

from enum import Enum, unique

@unique
class Model(Enum):
    Fast = "doubao-1.6-flash"
    Normal = "doubao-1.6"
    Thinking = "doubao-1.6-thinking"

# ========= 入口主流程 =========

def main():
    # 1) 读取课程表（统一所有工作表为单一列表）
    course_items = load_course_table("课程表.xlsx")

    # 2) 首问
    question_first = input('请问你遇到了什么问题？')

    # 3) 复杂度判断
    if is_complex_problem(question_first):
        print('这个问题比较复杂，我需要先帮你把问题说清楚，再给课。')

        # 3.1 初始化上下文
        ctx = {
            "original_question": question_first,
            "user_profile": {},       # 从用户回答中累计的角色/阶段/目标等
            "augmented_notes": "",    # 中间笔记/要点
        }

        # 3.2 专家式提问循环（尽快收敛到关键字段）
        # 目标：尽可能少问；凑齐关键字段就停
        while not has_enough_context(ctx):
            qs = generate_expert_questions(ctx, k=2)  # 控制每轮不超过 2 个问题
            # —— Coze 上可拆成一个“多轮追问”节点组 —— #
            answers = input("为了更准确推荐课程，请补充：" + " / ".join(qs) + "\n")
            ctx = update_context(ctx, answers)

        # 3.3 结构化输出 + 确认最后补充
        structured = structure_problem(ctx)   # 产出标准字段：role/stage/goals/pain/keywords/deliverable
        more = input("这是我理解的你的需求摘要：\n" + render_structured(structured) + "\n还有补充吗？(回车跳过)")
        if more.strip():
            ctx = update_context(ctx, more)
            structured = structure_problem(ctx)

        # 3.4 拆分并剔除伪问题
        sub_questions = decompose_and_filter(structured)

        # 3.5 课程推荐（支持一问多课 / 一课多问）
        recs = recommend_courses(sub_questions, course_items)

    else:
        print('这个问题比较清晰，我可以直接给你课程建议。')
        structured = quick_structure(question_first)    # 轻量抽取
        sub_questions = decompose_and_filter(structured)
        recs = recommend_courses(sub_questions, course_items)

    # 4) 输出结果（含匹配原因 + 选课链接）
    render_recommendations(recs)

def is_complex_problem(question):
    prompt = f'''<<<任务：判断是否为复杂问题>>>
请按以下六条进行量化评分（0-10）后仅输出整数：
1. 跨学科/多领域程度 2. 需要多步推理 3. 需要专业经验
4. 方案分支多样性 5. 长期影响 6. 伦理/治理考量
问题：{question}
仅输出 0-10 的整数。'''
    complexity = int(LLM(prompt, model=Model.Fast))
    return complexity > 5

def has_enough_context(ctx:dict)->bool:
    '''
    关键字段覆盖就算足够：
    - 角色/岗位（role）
    - 所处阶段（stage）
    - 目标/痛点（goals/pain 二选一）
    - 关键词（keywords 至少1个）
    - 期望交付（deliverable 可选但加分）
    '''
    prof = ctx.get("user_profile", {})
    ok = bool(prof.get("role")) and bool(prof.get("stage")) \
         and (prof.get("goals") or prof.get("pain")) \
         and prof.get("keywords")
    return ok

def generate_expert_questions(ctx:dict, k:int=2)->list[str]:
    '''
    基于现有空缺字段生成精准补问（最多 k 个）
    '''
    prof = ctx.get("user_profile", {})
    missing = []
    if not prof.get("role"):       missing.append("你的角色/岗位（如CEO/产品/工程/增长）？")
    if not prof.get("stage"):      missing.append("你所在项目/公司所处阶段（如Idea/MVP/PMF/增长/组织化）？")
    if not (prof.get("goals") or prof.get("pain")): missing.append("你想达成的目标或当前最痛的点是？")
    if not prof.get("keywords"):   missing.append("请给 1-3 个关键词（如“用户增长”“组织管理”“融资”）")
    if not prof.get("deliverable"):missing.append("更偏向学到哪类“交付模型/模板/方法论”？(可选)")

    return missing[:k] if missing else ["若有补充，请告诉我（可直接回车略过）。"]

def update_context(ctx:dict, user_text:str)->dict:
    '''
    把用户的自由文本更新成结构化 user_profile
    '''
    prof = ctx.get("user_profile", {})
    prompt = f'''<<<信息抽取（JSON）>>>
从下面文本抽取：role, stage, goals, pain, keywords(list), deliverable
文本：{user_text}
仅输出 JSON（缺失字段可为空）。'''
    extracted = LLM(prompt, model=Model.Normal)  # {'role':'产品','stage':'PMF','goals':'...','keywords':['...'],...}
    prof = merge_profile(prof, parse_json(extracted))
    ctx["user_profile"] = prof
    ctx["augmented_notes"] = (ctx.get("augmented_notes","") + "\n" + user_text).strip()
    return ctx

def structure_problem(ctx:dict)->dict:
    '''
    统一结构产物（也是推荐器的输入）
    '''
    return {
        "role": ctx["user_profile"].get("role", ""),
        "stage": ctx["user_profile"].get("stage", ""),
        "goals": ctx["user_profile"].get("goals", ""),
        "pain": ctx["user_profile"].get("pain", ""),
        "keywords": ctx["user_profile"].get("keywords", []),
        "deliverable": ctx["user_profile"].get("deliverable", "")
    }

def quick_structure(text:str)->dict:
    '''
    简化抽取：一次 LLM 抽取基础字段
    '''
    prompt = f'''<<<快速抽取>>>
从下面文本快速抽取 role/stage/keywords；goals/pain 二选一补齐。
文本：{text}
仅输出 JSON。'''
    return parse_json(LLM(prompt, model=Model.Fast))

# ========= 拆分与伪问题过滤 =========

def decompose_and_filter(structured:dict)->list[dict]:
    '''
    1) 拆分：把“大任务”拆成若干“可被课程直接赋能”的子问题
    2) 过滤：剔除伪问题（目标不清/与课程目标无关/不可被训练直接改善）
    '''
    prompt = f'''<<<问题拆分与过滤>>>
输入：{structured}
步骤：
- 把需求拆成 1-5 个可训练子问题（面向课程赋能）
- 标注每个子问题是否为伪问题（True/False），伪问题移除
输出：JSON 数组，每项含 title, reason, keywords(list)'''
    subqs = parse_json(LLM(prompt, model=Model.Thinking))
    return [q for q in subqs if not q.get("is_pseudo", False)]

# ========= 课程推荐（检索 + 启发式排序 + 解释） =========

def recommend_courses(sub_questions:list[dict], course_items:list[dict])->list[dict]:
    '''
    多对多匹配：
    - 每个子问题可对应多门课
    - 同一门课可覆盖多个子问题
    - 以“覆盖度 + 加权得分”排序，保证实用优先
    '''
    recommendations = []
    for q in sub_questions:
        scored = []
        for c in course_items:
            s, why = score_course_against_question(q, c)
            if s > 0:
                scored.append({
                    "score": s,
                    "why":  why,
                    "course": {
                        "课程名称": c.get("课程名称",""),
                        "课程方向": c.get("课程方向",""),
                        "所处阶段": c.get("所处阶段",""),
                        "核心训练": c.get("核心训练",""),
                        "主讲人":   c.get("主讲人",""),
                        "推荐谁学": c.get("推荐谁学",""),
                        "交付模型": c.get("交付模型",""),
                        "选课链接": c.get("选课链接",""),
                        "完成作业后解锁candy": c.get("完成作业后解锁candy","")
                    }
                })
        # 对单个子问题取 Top-K
        topk = sorted(scored, key=lambda x: (-x["score"], x["course"]["课程名称"]))[:5]
        recommendations.append({"sub_question": q, "courses": dedup_by_name(topk)})
    # 跨子问题再做一次“覆盖合并”与多样性重排（可选）
    return recommendations

def score_course_against_question(q:dict, c:dict)->tuple[int,str]:
    '''
    启发式打分（可在 Coze 用逻辑节点实现）：
    - 阶段匹配：q.stage in c["所处阶段"]          → +3
    - 角色/受众匹配：q.role in c["推荐谁学"]      → +2
    - 关键词命中：q.keywords ∩ (课程方向/核心训练) → 每命中 +1（上限+3）
    - 交付偏好：q.deliverable & c["交付模型"]存在  → +1
    - 子问题标题与核心训练语义相近（可加 LLM 判别）→ +0~2
    - 兜底：若完全无关则 0
    '''
    score = 0
    reasons = []

    # 阶段
    stage = q.get("stage","")
    if stage and stage in str(c.get("所处阶段","")):
        score += 3; reasons.append("阶段匹配")

    # 角色/受众
    role = q.get("role","")
    if role and role in str(c.get("推荐谁学","")):
        score += 2; reasons.append("受众匹配")

    # 关键词
    hits = 0
    kws = set([k.lower() for k in q.get("keywords",[])])
    hay = (str(c.get("课程方向","")) + " " + str(c.get("核心训练",""))).lower()
    for k in kws:
        if k and k in hay:
            hits += 1
    add = min(3, hits)
    if add>0:
        score += add; reasons.append(f"关键词命中{hits}个")

    # 交付
    if q.get("deliverable") and c.get("交付模型"):
        score += 1; reasons.append("有交付模型")

    # （可选）LLM 语义相似度加分 —— 此处仅占位示意
    # sim = semantic_match(q["title"], c["核心训练"])
    # if sim > 0.6: score += 2; reasons.append("语义相近")

    why = "、".join(reasons) if reasons else "规则未命中"
    return score, why

# ========= 输出渲染 =========

def render_recommendations(recs:list[dict]):
    '''
    统一的输出格式，便于 Coze 卡片化：
    - 子问题标题 + 推荐 Top-N 课程
    - 每门课包含：课程名称/方向/阶段/核心训练/主讲人/推荐谁学/交付模型/链接
    - 附“匹配原因”
    '''
    print("\n=== 课程推荐结果 ===\n")
    for block in recs:
        q = block["sub_question"]
        print(f"【子问题】{q.get('title','(未命名)')}")
        if not block["courses"]:
            print("  暂无匹配课程，建议换关键词或补充阶段/角色。\n")
            continue
        for item in block["courses"]:
            c = item["course"]
            print(f"- 课程：{c['课程名称']}｜方向：{c['课程方向']}｜阶段：{c['所处阶段']}")
            print(f"  主讲：{c['主讲人']}｜推荐：{c['推荐谁学']}｜交付：{c['交付模型'] or '—'}")
            print(f"  核心训练：{c['核心训练']}")
            print(f"  匹配原因：{item['why']}")
            print(f"  选课链接：{c['选课链接']}\n")

        if isinstance(v, list):

        else:
            out[k] = v

    return out

**成本考虑**

这里可以展开来分享一下。

在没有 AI 普及之前，token 还不是一个流行的概念，当时如果有谁说 token，可能人们会认为是在说类似 cookie 和 session 之类的话题。

后来我们进入了 AI 时代，很多人发现钱包疼了后，开始关注 token 这个概念了。

以至于概念太新，很多在线词典都没有把 「**词元**」这个释义纳入。

> 曾经看到一个说法，token 也可以被翻译为 「讨根」，在满足音译的同时，也表明了意义：人工智能可以和我们讨论问题，而 token 就是人类和 AI 沟通时，构成 **讨** 论问题所需的 **根** 本。

简单来理解，token 类似水电费和流量费，是对模型运行时背后资源消耗的一种计价度量。

扣子模型费用表

从 [扣子模型费用表](https://www.coze.cn/open/docs/coze_pro/model_fee) 可以看出，每一次模型调用，消耗的资源点和输入长度是阶梯计价的关系，这点和水电费很像。而且输出的费用是远大于输入的，直接高出了一个数量级。

> 这是因为生成（输出）token 需要 **每一步都重新跑一次完整的 Transformer 前向传播**（只要算一次注意力、前馈网络等），而输入 token 仅在 **模型开始时** 被处理一次，之后的每一步生成都可以直接复用已缓存的键/值向量。

是不是很像上课时，听老师讲课（输入）不咋费脑子，但是让自己开始写作业（输出）时就费劲多了：）

所以，我们有没有办法让模型的运行状态尽可能保持在这里？

### **第一性原理：AI 到底帮我们替代了什么？**

我们先做一个小小的思想实验。

假设这个世界上没有 AI，

我们仍然希望在一堂里，有一个「选课顾问」，帮每个同学做个性化选课。

你会怎么做？

答案其实很朴素：

**请一个很懂一堂、懂方法论、懂业务的人，坐在那儿，一对一问诊。**

这个人，我们叫他**「专家」**。

从物理层面来看，一个专家，是由几部分组成的：

- **能量：**心跳、呼吸、脑供血；
- **物质：**骨骼、肌肉、神经网络；
- **信息：**DNA、过往学习与实践积累、脑中连接权重。

但我们付钱买的是什么？

我们不是在买这堆能量、物质和信息。

我们买的是：**他坐在那儿，专注帮你思考那一段时间。**

钱本身不是基本物理量，时间才是。

有了 AI 之后，这个结构发生了微妙的变化：

- 我们用硬件，替代了人类身体的那部分物质载体；
- 我们用电力，替代了生理能量；
- 我们用模型权重，替代了部分信息积累。

结果是，我们有了一堆「专家的副本」：

- 它们可以 7×24 小时待命；
- 不会累，不会请假，只要有电，就能继续算。

我们过去是用钱，买专家那 8 小时的时间；

今天我们是用电费，买 AI 那 24 小时的计算。

在选课小助手这个项目里，我们做的事情，其实可以压缩成一句话：

> 我们用少量的电能，替代掉了原本需要大量专家时间来反复回答的「选课问诊」，
>
> 把这段时间还给了每一位一堂的用户。

这就是为什么在整个设计过程中，我会不断提醒自己：

> 我做的不是一个炫酷的 AI 玩具，
>
> 而是一台，帮别人和自己**省时间的小机器**。

### **熵与负熵：AI 是我们对抗信息混乱的工具**

如果再往下挖一层，这里面其实还有一条隐线：**熵**。

在没有任何工具帮助的情况下，

一个人在一堂面对上百门课，就是在面对一个高熵状态：

- 信息量巨大；
- 噪音混杂；
- 每做一个决策，都要消耗大量心理能量。

以前，我们如果想帮他，

我们的做法是——用自己的时间和精力，去看完、理解、归纳这些信息，

然后给他一套相对有序的、可执行的建议。

换句话说，

我们用自己的熵增，去换别人的熵减。

现在，有了结构化数据，有了工作流，有了模型，

我们可以把这件事变得聪明一点：

- 先花一段时间，把知识结构化，把流程搭起来；
- 然后，让机器在这条结构化流水线上，用电力来驱动计算。

从整个系统的角度看，

选课小助手其实是一台「小小的负熵装置」：

- 用户把一团乱麻一样的问题丢进来；
- 机器内部做了一大堆有序的处理；
- 最后吐出一份简洁的、结构化的行动建议。

所以，本质上，我们用的是电能，

来替代本该由人类脑力承担的那部分「对抗熵增的成本」。

### **一套可以带走的范式：任何大航海项目都能用**

【Tips🔧】到这儿，我想给大家留一个可以直接写进自己项目规划里的「四步法」。

你可以把它当成是今天这场分享里，

我递给大家的那件小小的「宝物」。

**第一步：把你的问题翻译成一条 IPO 流水线**

- 明确 Input：

  - 用户要提供哪些信息，才能做出好决策？
- 设计 Process：

  - 把大问题拆成一连串小 IPO，每个小节点只负责一件事
  - 能阴化的就阴化，能结构化的就结构化。
- 定义 Output：

  - 好的结果长什么样？
  - 从格式、字段，到呈现方式，都想清楚。

**第二步：把零散知识翻译成一个结构化底库**

- 找出你项目里的「CSV + Markdown」：

  - 哪些是躺在长文档里的经验？
  - 哪些是散在群聊、脑子里、云盘里的知识？
- 给它们一个「新家」：

  - 用表格、JSON 或者向量库，把它们整理成可查询、可更新的形式；
- 指定一个「唯一真相源」：

  - 决定所有更新最终以哪里为准。

**第三步：把人的角色，从操作员变成 MCP**

- 不要只把自己锁在「帮模型按按钮」的角色里
- 尽量把精力放在：

  - 怎么设计问题
  - 怎么设计上下文
  - 怎么设计反馈回路
- 让 AI 去承担中间大段的「算」和「试」，

人来负责「问得好」、「看得清」、「调得准」。

**第四步：把迭代翻译成一个 HITL 回路**

- 接受第一次一定不完美
- 把每一次偏差都当成一次反馈信号
- 用Y模型的视角：设预期 → 看偏差 → 找原因 → 调参数 → 再尝试。

### **回到「人」：用 AI 换来的，是不是更快乐的日子？**

最后，我想用一个稍微「唯心」一点的问题，

来作为我们这一段的收尾。

刚才我们从物理的角度讲了：

- 能量、物质、信息、时间；
- 专家和 AI；
- 熵增和电力。

但人活着，其实还有一个非常朴素的衡量标准：

**我开不开心，我爽不爽。**

所以我给自己留了三个问题，也想一并留给大家：

第一，用了 AI 之后，我自己，有没有**更快乐一点**？

第二，用到了我们做的这个选课小助手的一堂同学，会不会觉得**更轻松一点**，而不是更烦？

第三，我们这一队在做这件事情的过程本身，是不是一件**值得回忆**的事？

如果大部分时候，这三个问题的答案是「是的」，

那我觉得我们至少大方向没有走偏。

如果有一天，我们发现：

- 用 AI 只是为了堆 KPI
- 产品做出来，用户觉得麻烦
- 做项目的人自己也越来越痛苦

那可能我们就要停下来，

重新问一遍：

**我们是不是把本来用来对抗熵增的工具，*又变成了一台制造熵增的机器？***

## 答案

我们启程AI大航海，最终要寻得的宝藏，并不是 AI 本身。

**而是时间，更多的时间，更多自由的时间。**

AI 如此科幻的事情，发生的其实很快。谁知道之后会怎样呢？最后借用同样科幻的《三体》中的一句话作为结尾吧。

> 给岁月以文明，而不是给文明以岁月。
